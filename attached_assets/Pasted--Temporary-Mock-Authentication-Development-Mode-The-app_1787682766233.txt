# Temporary Mock Authentication — Development Mode

The application currently has **NO database and NO real authentication backend**.

For now, implement a **temporary local/mock authentication system** so I can fully test the Login, Sign Up, Profile, Change Password, Forgot Password, and Logout flows.

This is DEVELOPMENT MODE only.

## 1. Dummy Account Support

Allow users to create accounts with any valid-looking email address and password.

Example:

```text
Email:
asad@example.com

Password:
12345678
```

The application should NOT require the email to exist in a real database.

For development purposes, save the mock account locally using the appropriate local storage mechanism for the existing framework.

---

## 2. Mock Registration

When the user uses:

**Sign Up → Create Account**

accept the registration if:

* Name is provided
* Email has valid email format
* Password meets the application's minimum password requirement
* Confirm password matches

Then save something similar to:

```text
User
├── id
├── name
├── email
├── password
└── profile information
```

The password is acceptable to store locally ONLY because this is a temporary development/mock authentication system.

Add a clear code comment that this must NOT be used in production.

## 11. Architecture Requirement

IMPORTANT:

Do not tightly couple the UI directly to local storage.

Create a clean authentication abstraction, for example:

```text
AuthService
    ↓
MockAuthService
    ↓
Local Storage
```

The UI should communicate with `AuthService`, not directly with local storage.

This is important because later I will replace:

```text
MockAuthService
```

with something like:

```text
FirebaseAuthService
```

or:

```text
SupabaseAuthService
```

or:

```text
BackendAuthService
```

without having to redesign the entire application.

---

## 12. Development vs Production

Create a clear separation between development/mock authentication and future production authentication.

Use a configuration/environment flag such as:

```text
AUTH_MODE=mock
```

For now:

```text
AUTH_MODE=mock
```

Later:

```text
AUTH_MODE=production
```

Do not expose demo credentials or development bypasses in production builds.

## 13. Important Security Warning

This is ONLY temporary development authentication.

Do NOT present this implementation as secure production authentication.

When the real backend/database is integrated later:

* Passwords must not be stored as plain text.
* Authentication must be handled securely.
* Sessions/tokens must be managed securely.
* Password reset must use a real secure mechanism.
* Demo accounts must be removed.
* Development bypasses must be removed.

Add TODO comments in the relevant code indicating where the real authentication implementation must replace the mock implementation.
